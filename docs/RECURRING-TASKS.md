# Recurring tasks: standards and client behavior

This document records what the standards say about recurring tasks (`VTODO`
with `RRULE`) and how widely used CalDAV clients handle them: what they write
when a user completes or moves one occurrence, and how they read what other
clients wrote. It is the basis for how Lucid shows and edits recurring tasks
(FR-16, FR-17), which [Lucid's behavior](#lucids-behavior) describes.

The survey was done on 2026-09-29. Client behavior changes, so every finding
names the release or commit it was read at, and every claim carries one of
these labels:

- **code**: read in the client's source at the linked commit
- **issue**: from an issue, the docs, or iCalendar data captured by others
- **inferred**: our deduction from code or reports, not observed directly
- **unknown**: searched for, not found

## Summary

- **RFC 5545 does not define how to complete one occurrence of a recurring
  task.** The only per-occurrence mechanism it has is the override component
  (`RECURRENCE-ID`). Advancing the master's `DTSTART`/`DUE` is valid
  iCalendar, but it redefines the series instead of recording a completion.
- **Clients use three incompatible models**: an override per occurrence
  (Thunderbird, SOGo, jtx Board), rolling the master forward, often plus a
  completed copy under a new UID (Apple Reminders, Tasks.org, Evolution,
  OpenTasks, Nextcloud Tasks, Outlook via CalDAV Synchronizer, Roundcube/Kolab,
  InfCloud), and private schemes (KDE's `X-KDE-LIBKCAL-DTRECURRENCE`). Some
  clients just complete the master, which ends the series (GNOME Errands,
  GNOME Endeavour).
- **Few clients read overrides, and on three common paths they cause harm.**
  Tasks.org stops fetching the whole calendar at a resource with an override.
  DAVx⁵ drops overrides on the way to OpenTasks and Tasks.org and can delete
  them from the server on the next upload. Outlook CalDAV Synchronizer deletes
  them whenever it writes.
- **Rolling the master is the only write that every surveyed client shows
  sensibly.** Its cost is that completed occurrences leave no trace in the
  series.
- **Moving one occurrence on its own needs an override**, with the same
  interoperability problems. Under the rolling model a move changes the
  master, so the future moves with it (interval rules) or the result is
  undefined (rules with fixed days).
- **Readers must expect recurring tasks without `DTSTART`**, although RFC 5545
  requires it: Tasks.org anchors recurrence on `DUE` and often writes no
  `DTSTART`.

## What the standards say

### RFC 5545 (iCalendar)

- `DTSTART` is required with `RRULE`: *"This property is REQUIRED in all types
  of recurring calendar components that specify the "RRULE" property."*
  ([§3.8.2.4](https://www.rfc-editor.org/rfc/rfc5545#section-3.8.2.4))
- The recurrence set is anchored on `DTSTART` only: *"The recurrence set is
  generated by considering the initial "DTSTART" property along with the
  "RRULE", "RDATE", and "EXDATE" properties … The "DTSTART" property defines
  the first instance in the recurrence set. The "DTSTART" property value SHOULD
  be synchronized with the recurrence rule, if specified. The recurrence set
  generated with a "DTSTART" property value not synchronized with the
  recurrence rule is undefined."*
  ([§3.8.5.3](https://www.rfc-editor.org/rfc/rfc5545#section-3.8.5.3))
- Each instance has the same duration: *"If the duration of the recurring
  component is specified with the "DTEND" or "DUE" property, then the same
  exact duration will apply to all the members of the generated recurrence
  set."* (§3.8.5.3). An instance's `DUE` is its start plus the master's
  `DUE − DTSTART`.
- With `COUNT`, *"The "DTSTART" property value always counts as the first
  occurrence."* ([§3.3.10](https://www.rfc-editor.org/rfc/rfc5545#section-3.3.10))
- `RECURRENCE-ID` *"is the original value of the "DTSTART" property of the
  recurrence instance"* and *"allows the reference to an individual instance
  within the recurrence set"*
  ([§3.8.4.4](https://www.rfc-editor.org/rfc/rfc5545#section-3.8.4.4)).
- `STATUS` *"defines the overall status or confirmation for the calendar
  component"* ([§3.8.1.11](https://www.rfc-editor.org/rfc/rfc5545#section-3.8.1.11)),
  and `COMPLETED` is *"the date and time that a to-do was actually completed"*
  ([§3.8.2.1](https://www.rfc-editor.org/rfc/rfc5545#section-3.8.2.1)).
  Neither mentions recurrence, and the `VTODO` section (§3.6.2) says nothing
  about it either.

What follows from this is our interpretation:

- The RFC is **silent** on completing one occurrence. An override with
  `RECURRENCE-ID`, `STATUS:COMPLETED` and `COMPLETED` uses the only
  per-instance mechanism the RFC has.
- `STATUS:COMPLETED` on the master reads as "the whole series is done".
- Advancing the master's `DTSTART` is not forbidden, but earlier instances drop
  out of the set, and nothing records which instance was completed. With
  `COUNT`, each advance adds one instance at the end unless `COUNT` is lowered
  too. Overrides whose `RECURRENCE-ID` now lies before `DTSTART` no longer
  match any instance, and the RFC does not say what that means.

### RFC 5546 (iTIP)

A `VTODO` `REPLY` carries `RECURRENCE-ID` *"Only if referring to an instance
of a recurring calendar component"* (§3.4.3). The non-normative example
[§4.5.7.2](https://www.rfc-editor.org/rfc/rfc5546#section-4.5.7.2), "Replying
to an Instance of a Recurring VTODO", reports `PERCENT-COMPLETE:75` for one
instance that way. This is the closest precedent for per-occurrence progress.

### RFC 4791 (CalDAV)

- All components with the same `UID` must be in one calendar object resource
  ([§4.1](https://www.rfc-editor.org/rfc/rfc4791#section-4.1)), so overrides
  live in the master's resource.
- Time-range filters *"MUST consider every recurrence instance"*, and the
  server has to *"infer an effective value for DTSTART, DTEND, DURATION, and
  DUE properties for an instance based on the recurrence patterns and any
  overrides"* ([§9.9](https://www.rfc-editor.org/rfc/rfc4791#section-9.9)).
  `STATUS` plays no part in that, so completed instances still match.

### RFC 8984 (JSCalendar)

- A task recurs from `start`, or from `due` if there is no `start` (§4.3.3).
  JSCalendar allows what iCalendar does not.
- Per-occurrence changes go into `recurrenceOverrides`. A `progress` override
  is the equivalent of an iCalendar override (interpretation).
- [§5.2.6](https://www.rfc-editor.org/rfc/rfc8984#section-5.2.6) is the only
  standards text found that addresses progress on one occurrence of a
  recurring task. It is about the `progressUpdated` timestamp, and it names
  both approaches without preferring one: *"One way to achieve this is
  by overriding the "progressUpdated" property in the task
  "recurrenceOverrides" property. However, this could produce a long list of
  timestamps … An alternative approach is to split the Task into a current,
  single instance … and a future recurring instance."*

### Other RFCs and drafts

- RFC 7986 and RFC 9073 say nothing on recurrence or completion. RFC 9074
  covers acknowledging alarms of recurring to-dos only.
- RFC 9253 `RELTYPE=FIRST/NEXT` can link the parts of a split series but says
  nothing about completion.
- `draft-ietf-calext-ical-tasks` (in final review as RFC 10051, September
  2026) adds `VSTATUS`, `SUBSTATE`, `TASK-MODE` and `ESTIMATED-DURATION`; the
  word "recur" does not occur in it
  ([final review](https://github.com/rfc-editor-drafts/FinalReview-rfc10051)).
- The expired `draft-ietf-calext-icalendar-series` notes that *"The RFC5545
  THISANDFUTURE range is poorly supported. Splitting is the approach a number
  of implementations use"*, and that relating the parts *"is not
  standardized"*.
- "Repeat from completion date" (Tasks.org, Outlook's "regenerate") is not
  defined anywhere.

## Models for completing one occurrence

### Override

The master stays unchanged. The completed occurrence becomes an override in
the same resource:

```
BEGIN:VTODO                      ← master, unchanged
UID:abc
DTSTART:20260907T090000Z
DUE:20260907T100000Z
RRULE:FREQ=WEEKLY
END:VTODO
BEGIN:VTODO                      ← completed occurrence
UID:abc
RECURRENCE-ID:20260914T090000Z
DTSTART:20260914T090000Z
DUE:20260914T100000Z
STATUS:COMPLETED
COMPLETED:20260914T093000Z
PERCENT-COMPLETE:100
END:VTODO
```

Every occurrence can be completed or moved on its own, and the history stays
in the series. It needs readers that expand the series and match overrides.

### Rolling

The master moves to the next occurrence and stays open:

```
BEGIN:VTODO
UID:abc
DTSTART:20260921T090000Z         ← was 20260914T090000Z
DUE:20260921T100000Z
RRULE:FREQ=WEEKLY;COUNT=3        ← was COUNT=4, where the client decrements
STATUS:NEEDS-ACTION
END:VTODO
```

Variants:

- **COUNT**: Tasks.org, Evolution and Nextcloud Tasks lower it by one,
  OpenTasks by the number of skipped occurrences. Apple never writes `COUNT`
  (it turns "repeat N times" into an `UNTIL`), and Kolab converts `COUNT` to
  `UNTIL`.
- **Completed copy**: Apple Reminders, OpenTasks, Outlook CalDAV Synchronizer,
  Kolab and InfCloud also store the completed occurrence as a separate
  resource with a **new UID**, usually unlinked. Kolab links it with
  `RELATED-TO;RELTYPE=PARENT`, and Outlook's copy still carries the `RRULE`.
- **Last occurrence**: most clients then set `STATUS:COMPLETED` on the master
  and keep the `RRULE` (Apple, Tasks.org, Evolution, Nextcloud Tasks, Kolab).
  OpenTasks removes the `RRULE` and deletes the master.

Any client can read the result, because it is a plain series that starts
later. Completed occurrences leave no trace in the series.

### Other schemes

- **KDE** keeps `DTSTART`/`DUE` at the first occurrence and moves the pending
  occurrence in the private property `X-KDE-LIBKCAL-DTRECURRENCE`.
- **Completing the master** ends the series (GNOME Errands, GNOME Endeavour,
  and Lucid at the time of the survey).

## Client survey

### Overview

| Client | Completing an occurrence writes | Overrides from other clients | Shows occurrences |
|---|---|---|---|
| Thunderbird | override | shown | calendar views; task list depends on filter |
| SOGo | override | shown | task list (±1 year); no tasks in calendar grid |
| jtx Board | override | shown | yes |
| Nextcloud Calendar | nothing (read-only) | shown | calendar grid |
| KDE (KOrganizer, Merkuro) | `X-KDE-LIBKCAL-DTRECURRENCE` | agenda: shown; task list: extra row | agenda and month views |
| Evolution | rolling, `COUNT − 1` | extra row, master looks overdue | no |
| Tasks.org | rolling (anchor `DUE`), `COUNT − 1` | **fetch of the whole calendar stops**; can be lost on upload | no |
| DAVx⁵ → OpenTasks / Tasks.org | – | **dropped, deleted on next upload** | – |
| DAVx⁵ → jtx Board | – | round-trip | – |
| OpenTasks | rolling + completed copy | never reaches it (DAVx⁵) | next open one only |
| Apple Reminders | rolling + completed copy | not supported (2020), today unknown | no |
| Nextcloud Tasks | rolling, `COUNT − 1` | ignored, kept on write | no |
| Outlook CalDAV Synchronizer | rolling + completed copy (keeps `RRULE`) | **deleted on write** | no |
| Roundcube (Kolab tasklist) | rolling + linked copy | ignored | no |
| InfCloud | default: rolling + copy; RFC mode: override | default: ignored | default: first only |
| GNOME Errands, Endeavour | master completed, series ends | ignored | no |

### Tasks.org

Read at [`626d683`](https://github.com/tasks/tasks/tree/626d68312e3b3075e158bf384119e72889a913eb)
(main, 2026-09-29; the same logic is in release 15.12).

**Write**

- Completing moves `DUE` to the next occurrence and `DTSTART` by the same
  amount, clears `COMPLETED`, `STATUS` and `PERCENT-COMPLETE`, and lowers
  `COUNT` by one. `UNTIL` stays. It writes no override, no `EXDATE` and no
  copy. **code**
  ([RepeatTaskHelper.kt#L41-L78](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/com/todoroo/astrid/repeats/RepeatTaskHelper.kt#L41-L78),
  [Task.kt#L120-L127](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/data/src/commonMain/kotlin/org/tasks/data/entity/Task.kt#L120-L127))
- An existing start date moves with the due date; a task without one never
  gets one on completion (`setDueDateAdjustingHideUntil` only shifts
  `hideUntil` when it is set). **code**
  ([Task.kt#L120-L126](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/data/src/commonMain/kotlin/org/tasks/data/entity/Task.kt#L120-L126))
- On the last occurrence (`COUNT=1`, or the next date is past `UNTIL`) the task
  stays `COMPLETED` with its `RRULE`. **code**
  ([RepeatTaskHelper.kt#L53-L59](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/com/todoroo/astrid/repeats/RepeatTaskHelper.kt#L53-L59))
- Recurrence is anchored on `DUE`; without `DUE` the next date is counted from
  now. **code**
  ([RepeatTaskHelper.kt#L231-L246](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/com/todoroo/astrid/repeats/RepeatTaskHelper.kt#L231-L246))
- `DTSTART` is only written if the task has a start date, so recurring tasks
  created in Tasks.org often have `DUE` and `RRULE` but no `DTSTART`. **code**
  ([iCalendar.kt#L449-L488](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/org/tasks/caldav/iCalendar.kt#L449-L488))
- "Repeat from completion date" is local only and never synced. **code**
- For Open-Xchange and mailbox.org accounts the server advances the task
  instead. **code**
  ([TaskCompleter.kt#L88](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/org/tasks/service/TaskCompleter.kt#L88))
- Uploads send no `If-Match`. **code**
  ([CaldavSynchronizer.kt#L458](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/org/tasks/caldav/CaldavSynchronizer.kt#L458))

**Read**

- No expansion: one resource is one task, shown at its `DUE`. **code**
- `DTSTART` is the task's start date (`hideUntil`, "Starts" in the editor): an
  all-day `DTSTART` the start of that day, a timed one that instant. **code**
  ([iCalendar.kt#L346-L354](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/org/tasks/caldav/iCalendar.kt#L346-L354),
  [TaskExtensions.kt#L23-L42](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/org/tasks/data/TaskExtensions.kt#L23-L42))
- Tasks whose start date lies ahead are shown by default: the filter that
  hides them only applies while "Show unstarted" in a list's sort menu is
  off, and `showHidden` defaults to true. **code**
  ([TaskDao.kt#L265-L274](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/data/src/commonMain/kotlin/org/tasks/data/dao/TaskDao.kt#L265-L274),
  [SortHelper.kt#L77-L89](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/com/todoroo/astrid/core/SortHelper.kt#L77-L89),
  [Preferences.kt#L598-L600](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/app/src/main/java/org/tasks/preferences/Preferences.kt#L598-L600))

  resources, remote deletions and the ctag update. Because the ctag is not
  stored, this repeats on every sync. **code**
  ([iCalendar.kt#L383-L393](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/org/tasks/caldav/iCalendar.kt#L383-L393),
  [CaldavSynchronizer.kt#L350-L354](https://github.com/tasks/tasks/blob/626d68312e3b3075e158bf384119e72889a913eb/kmp/src/commonMain/kotlin/org/tasks/caldav/CaldavSynchronizer.kt#L350-L354))
- The maintainer confirmed that Tasks.org does not parse resources with
  several `VTODO`s ([#2270](https://github.com/tasks/tasks/issues/2270),
  2024-12-25). Support exists on a branch but is not merged
  ([#3360](https://github.com/tasks/tasks/issues/3360), 2026-07-02). **issue**

**Interop**

- Uploads still run after the aborted fetch, without `If-Match`. Completing
  such a task in Tasks.org replaces the resource with a single `VTODO` and
  loses the other client's overrides. **inferred**
- Completions don't sync between Tasks.org and Thunderbird or KDE in either
  direction ([#1600](https://github.com/tasks/tasks/issues/1600),
  [#3360](https://github.com/tasks/tasks/issues/3360)). #3360 also argues that
  moving `DUE` violates RFC 5545. **issue**
- Thunderbird completing a Tasks.org task moves the start but not the due date

## Moving one occurrence

### With an override

Only that occurrence moves: the override keeps the original start as
`RECURRENCE-ID` and gets its own `DTSTART`/`DUE`. **Future occurrences stay on
the rule.** Thunderbird asks "only this occurrence / all occurrences" and
writes such an override.

It is the same override as for completing, with the same problems:
Tasks.org's sync of that calendar stalls, DAVx⁵ (to OpenTasks or Tasks.org)
and Outlook CalDAV Synchronizer delete the override on their next write (the
occurrence silently jumps back), and Apple, Nextcloud Tasks and Evolution keep
showing the occurrence at its old date. If a rolling client later advances
the master past it, the override no longer matches any occurrence.

For "this and all following" RFC 5545 has `RANGE=THISANDFUTURE`, which is
poorly supported. Clients usually split the series instead: the old one ends
with `UNTIL`, and a new one starts at the moved occurrence.

### Under the rolling model

There is no "only this one": the master *is* the current occurrence, so a
move changes the master's `DTSTART`/`DUE`. What happens to the future depends
on the rule:

- **Interval rules** (`FREQ=DAILY`, `FREQ=WEEKLY` without `BYDAY`,
  `INTERVAL=2`, …): the future is recomputed from the new date, so every later
  occurrence moves along. "Every 2 weeks" moved from Monday to Wednesday means
  every other Wednesday from now on.
- **Rules with fixed days** (`BYDAY=MO`, `BYMONTHDAY=15`, …): the future stays
  on the rule's days, and the moved occurrence no longer matches the rule, so
  RFC 5545 calls the result undefined. In practice readers show the moved date
  once and then the rule's days again: Lucid's `expandSeries` always includes
  `DTSTART`, and Tasks.org computes the next occurrence from `DUE` to the next
  rule day. That behaves like "only this one", without a guarantee.

Shifting a whole series by the distance one occurrence moved has the same
problem: the dates move, but `BYDAY`/`BYMONTHDAY` do not.

## Pitfalls for readers

- **Series without `DTSTART`** (Tasks.org): Thunderbird expands from `DUE` but
  keeps `DUE` fixed per occurrence, KDE copies `DUE` into `DTSTART`, Evolution
  rolls it from the wall clock instead of from `DUE`, jtx Board doesn't expand
  it, Nextcloud Calendar drops the task, eM Client failed to sync it.
  Anchoring on `DUE` in that case matches JSCalendar and Tasks.org.
- **A completed master with `RRULE`** usually means the series has ended
  (Apple, Tasks.org, Evolution, Nextcloud Tasks, Kolab), but it also results
  from clients that complete the master directly (Errands, Endeavour) and from
  Outlook's completed copies. Expanding it shows every occurrence as done
  (Nextcloud Calendar does this).
- **Completed copies** (Apple, OpenTasks, Kolab, Outlook, InfCloud) are
  separate tasks with a new UID; nothing but `RELATED-TO` (Kolab only) ties
  them to the series.
- **Overrides before the master's `DTSTART`** remain after a rolling client
  advanced the master. They no longer belong to an instance.
- **`RECURRENCE-ID` in another form** than `DTSTART` (UTC versus `TZID`,
  floating, missing `VALUE=DATE`): compare instants, not strings (jtx Board
  compares strings; Nextcloud Tasks would write floating values).
- **Writers without `If-Match`** (Tasks.org) can overwrite concurrent changes.
- **A second resource with the same UID** is rejected by Nextcloud (409);
  RFC 4791 §4.1 requires one resource per UID.
- **All-day `DUE`**: inclusive or exclusive differs between clients (eM Client
  treats it as exclusive since 2026-02).
- **An `RRULE` a client can't handle** can stop the whole list from syncing
  (iOS, Nextcloud Tasks).

## Lucid's behavior

Lucid shows every occurrence of a recurring task in the calendar views and
lets the user complete and move the current one (FR-16, FR-17). The API is
described in [API.md](API.md#todos).

**Decision (2026-09-29): write by rolling, read tolerantly.**

- **Why rolling**: it is what most clients write, and the only write that
  every surveyed client shows sensibly. Overrides are more faithful to
  RFC 5545 and would allow per-occurrence completion and moves, but only
  Thunderbird, SOGo and jtx Board write them, and on three common paths
  (Tasks.org, DAVx⁵ to OpenTasks/Tasks.org, Outlook CalDAV Synchronizer) they
  stall a calendar's sync or get deleted silently. The worst case of rolling
  is lost history; the worst case of overrides is a stalled calendar or data
  loss.
- **Why a completed copy**: rolling alone leaves no trace of a completion. A
  copy under a new UID, as Apple Reminders, OpenTasks, Kolab and InfCloud
  write it, keeps the history, and every client shows it as a plain completed
  task. Nothing links it to the series; only Kolab uses `RELATED-TO` for that.
- **Reading** handles all models: overrides written by other clients
  (completed, moved, cancelled), series anchored on `DUE` when `DTSTART` is
  missing, completed masters, and completed copies as tasks of their own.
  Because Lucid reads overrides anyway, a later switch of the write model
  stays cheap.
- **Why in order, and why a move window**: under the rolling model the master
  *is* the current occurrence, so only it can be completed or moved. With a
  rule on fixed days, a move past the next occurrence would drop the
  occurrences in between, and a move before the current one would bring it
  back (see [Moving one occurrence](#moving-one-occurrence)). The UI keeps
  such a move in between.

### Reading

- A `VTODO` with `RRULE` recurs from its `DTSTART`, or from its `DUE` when it
  has no `DTSTART` (Tasks.org), in the time zone of its `TZID`. The due of an
  occurrence is its start plus the master's `DUE − DTSTART` (or `DURATION`).
- The **current occurrence** is the earliest one that no override completes
  or cancels and no `EXDATE` excludes, counted from `DTSTART` or from KDE's
  `X-KDE-LIBKCAL-DTRECURRENCE`, whichever is later. The task list and the API
  show the series at this occurrence, with the one after it as `next`.
- An override belongs to the occurrence whose `RECURRENCE-ID` is the same
  instant, in whatever form it is written. A completed override is a **done**
  occurrence, also before `DTSTART`, where a rolling client left it behind. An
  override with other dates moves its occurrence; a cancelled override or an
  `EXDATE` removes it.
- A completed or cancelled master is shown once, as a completed task, and not
  expanded. Completed copies, Lucid's or another client's, are tasks of their
  own.
- A series Lucid cannot evaluate is shown once, at its stored dates, marked
  `ruleUnsupported`: an `RRULE` it cannot parse or cannot evaluate within
  100,000 iterations, any `RDATE`, and a series with neither `DTSTART` nor
  `DUE`, which shows in the task list only. Rolling cannot keep an `RDATE`
  off the rule without shifting the rule, and task series with `RDATE` are
  rare. Such a series cannot be completed, moved or given a new rule in
  Lucid; its other fields can be edited, and its rule removed.
- A view asks for at most 366 days, with at most 1,000 occurrences per
  series.

### Writing

**Completing** the current occurrence writes two resources, as Apple
Reminders does:

1. A completed copy under a new UID (`If-None-Match: *`): the occurrence's
   dates in the form the series writes them (a `DATE`, the same `TZID` with
   its `VTIMEZONE`, floating, or UTC), `SUMMARY`, `DESCRIPTION` with the
   checklist, `PRIORITY`, `STATUS:COMPLETED`, `COMPLETED` and
   `PERCENT-COMPLETE:100`, but no rule and no alarms.
2. The rolled master (`If-Match`): `DTSTART` and `DUE` move to the next
   occurrence's place in the rule, in the form they are written in. A series
   anchored on `DUE` gets a `DTSTART` equal to `DUE`, since RFC 5545 requires
   `DTSTART` with `RRULE`. The master is open again (`STATUS:NEEDS-ACTION`,
   no `COMPLETED` or `PERCENT-COMPLETE`), with its checklist unchecked. A
   `COUNT` becomes the `UNTIL` of the rule's last instance, in the form of
   `DTSTART`, so that later rolls keep the end without counting down. The
   override of the completed occurrence and KDE's pending occurrence go; an
   override of the next occurrence stays, so that an occurrence moved in
   another client stays moved.

If the master cannot be written, for example because another client changed
it in the meantime, Lucid deletes the copy again and reports the error. The
last occurrence gets no copy: the master itself becomes `COMPLETED` and keeps
its `RRULE`, as with Apple, Tasks.org and Evolution. Undo writes the master's
previous dates, status and checklist back, then deletes the copy.

A series anchored on `DUE` gets its `DTSTART` because RFC 5545 requires one
with `RRULE`, and because the readers above do better with it: Thunderbird
then gives every occurrence its own due date, Evolution rolls from the series
instead of from the wall clock, jtx Board expands the series at all, and
iCloud keeps the time of a timed due. Tasks.org reads it as the task's start
date: with its default, "Show unstarted" on, nothing changes there; with it
off, a timed series shows only from its due time on. Lucid's own editor shows
the series with a start equal to its due date from the first completion on.

**Moving** the current occurrence writes the new dates to the master's
`DTSTART` and `DUE`, in the form they are written in (a series anchored on
`DUE` gets a `DTSTART` here too), and drops that occurrence's override and
KDE's pending occurrence. What refers to later occurrences stays with them:

- With an interval rule, their overrides (`RECURRENCE-ID`, `DTSTART`, `DUE`),
  `EXDATE`s and an `UNTIL` from the moved occurrence on move by the same
  amount, in the wall clock of the series, so across a change of daylight
  saving time too.
- With fixed days they move by the change in time of day only, because the
  rule's days stay.
- A move that keeps the rule's instances where they are, such as undoing a
  completion, moves none of them; an `UNTIL` on the occurrence the master
  had rolled to stays too, so the series ends where it did before the
  completion.

A `COUNT` no longer counts the rule's instances before the moved occurrence.
An `UNTIL` that would end before the new date moves onto it: clients built
on ical.js, such as Thunderbird, hide a task whose `DTSTART` lies after its
`UNTIL`. The backend does not enforce the move window: other clients write
any date, and undo has to move a series back.

**Setting or changing a rule** applies it from the current occurrence on: its
dates become `DTSTART` and `DUE`, and a task that did not recur yet writes
timed dates with the browser's time zone as `TZID` (and a `VTIMEZONE`), like
a recurring event. Overrides from the current occurrence on go; earlier
ones, the completed occurrences, stay. A rule needs a start or due date. The
editor only sends a rule the user changed: a preset writes a stored rule in
its own words, which would count as a new rule and start the series over.

**Removing the rule** leaves a single task at the current occurrence's dates,
without `RRULE`, `RDATE`, `EXDATE` or overrides, as for events. **Deleting** a
series deletes its resource; completed copies stay. Every write keeps the
properties and components Lucid does not know.

### Limits

- Only the current occurrence can be completed, so occurrences are completed
  in order. Later ones are a preview, and none can be skipped.
- An occurrence cannot be moved on its own: moving it moves the series from
  the current occurrence on. With an interval rule the later occurrences move
  along. With fixed days the calendar, the editor and the date picker in the
  task list keep the move between the current occurrence's day and the day
  before the next occurrence; the time of day is free within those days.
- A completed copy is not linked to its series: later edits of the series
  don't change it, and deleting the series keeps it.
- Undoing a completion is a move back onto the completed occurrence, and a
  move drops the override of the occurrence it moves from: an occurrence
  another client had moved, which the completion rolled onto and kept, loses
  that override when the completion is undone.
- A `COUNT` counts from `DTSTART` (RFC 5545), so a series whose `DTSTART`
  another client left off its rule has one occurrence more than its `COUNT`
  says, the anchor itself; the `UNTIL` a completion writes keeps that extra
  one.
- A series in a `TZID` Lucid cannot resolve is read at its wall clock as UTC,
  and the `UNTIL` a completion writes for its `COUNT` is that wall clock as
  UTC. In a zone west of UTC it lies before the last occurrence's real
  instant, so a reader that knows the zone may end the series one occurrence
  early.
- A move of a `MONTHLY` or `YEARLY` interval series shifts the references to
  later occurrences by the calendar days the current occurrence moved, not by
  months, so an override or `EXDATE` can end up off its occurrence when the
  months differ in length.
- Removing a rule also removes other clients' overrides, completed ones
  included.
- Moving an occurrence of a recurring **event** still moves the whole series,
  without adjusting `BYDAY`/`BYMONTHDAY`.
- "Repeat from completion date" is not supported; Tasks.org keeps it local,
  and no standard defines it.

### Where the UI shows it

The UI speaks of *repeats*, never of copies or overrides. For those who want
to know more, an ⓘ next to the repeat in the editor explains that a completed
repeat stays as its own entry while the task moves on to the next one, and
that repeats are completed in order.

- **Calendar views**: the current occurrence looks like any task, with a
  checkbox and ⟳, and can be dragged. Upcoming ones are pencilled in: a dashed
  outline in the calendar's color, no checkbox, not draggable; a click opens
  their details. Done ones look like completed tasks, and "Hide in calendar"
  hides them too; one completed by another app cannot be reopened.
- **Task list**: one row per series, due at its current occurrence, with ⟳
  and the rule as screen reader text. Completed copies are completed tasks.
- **Details**: the rule in words; for an upcoming occurrence "Can be completed
  once *date* is done."; for one completed by another app "Completed in
  another app."; for a rule Lucid cannot evaluate "Lucid can't read this
  repeat. Complete and move it in the app that created it."
- **Editor**: a repeat field with "Does not repeat" and every day, week,
  month or year on the day of the task's start, else its due date. A rule
  from another app stays as "Custom rule" until another is chosen. A series
  shows "This task repeats. Changes apply to all upcoming repeats.", and a
  rule without a date is refused with "A repeating task needs a date."
- **Date pickers**: days outside the move window are blocked but stay
  reachable by keyboard, with "Until *date*, then the next repeat is due."
- **Dragging**: days outside the move window are hatched. A drop there
  changes nothing, and screen readers hear "Only possible until *date*."
- **Toasts**: "Done. Next up: *date*", "Done. That was the last repeat.",
  "Moved to *date*. Then: *date*" and, for the last repeat, "Moved to
  *date*.", each with Undo for 8 seconds, then "Undone."
- **Deleting** asks "This task repeats. Delete all repeats? Completed ones
  stay."
